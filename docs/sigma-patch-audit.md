# D2Sigma patch audit: what Median changes in the original game code, and what the port does about it

Lane `audit-patches`, 2026-10-22. Median XL 2.14.4 puts most of its engine changes in `D2Sigma.dll`. Much of it shows up as
tables the port already converts (skills, missiles, item spells, calc codes). The rest is **D2Sigma patching the original
1.13c DLLs at run time** (D2Game, D2Client, D2Common, ...). No table points at those, so they were easy to miss: Median leaves
no player corpse, and for a long time no doc said so. This file lists every one of those patch sites, says what the original
code did and what Median makes it do, and gives each a port status. The raw site list is
[`research/sigma_patches.tsv`](../research/sigma_patches.tsv) (`.json`), made by [`tools/sigma_patches.py`](../tools/sigma_patches.py);
the audited rows are [`research/sigma_patch_audit.tsv`](../research/sigma_patch_audit.tsv).

Related: [unported.md](unported.md) (every **missing** row below is also there as `open`), [d2r-addresses.md](d2r-addresses.md)
Appendix B (the D2Game patch table grouped by Sigma target), [services.md](services.md), [subsystems/](subsystems/).
Overlap with other lanes: `audit-rules` audits the same gap from the player-rules side (rows marked "overlap audit-rules");
`no-corpse` is porting the death handling (rows marked "lane no-corpse").

## 1. The mechanism, and why the list is complete

* `DllModInit` of D2Sigma calls `FUN_10043d60`, which calls the patcher `FUN_10044750` once per module
  (ecx = module index, edx = process handle, stack = table pointer). Module names: `0x101d4014` (12-byte entries,
  23 modules from Game.exe to Storm).
* There are **19 static tables**, one per module (the D2Glide table only when `-noglide` is not given; D2MCPClient's is empty).
  A table is a dword header, then 5-dword records `{rva, size, value, relative, module}`, ended by a record with rva 0.
  * `size = 0`: write the dword `value` (a constant, a pointer, or the single byte `0xe9` / `0xe8` of a jmp/call whose rel32 is
    the next record at rva+1).
  * `size = N`: fill N bytes with the low byte of `value` (`0x90` nops, or one byte such as `0xeb`).
  * `relative`: write the rel32 `value - (address + 4)`, so the operand of an existing call/jmp now reaches D2Sigma code.
* The writes go through `VirtualProtect` / `WriteProcessMemory`, which D2Sigma imports and only this patcher calls. D2Sigma has
  no detour library, no IAT patching and no other store into a game-DLL address range: a search of the D2Sigma code for stores
  through the 236 game `.data` pointers in `research/sigma_imports.json` found none. `DllModInit` also loads `d2fps.dll` (a frame-rate
  limiter, no game logic).
* So **the 19 tables are the complete set of run-time changes to game code and data**: 2,121 raw writes, grouped by
  `tools/sigma_patches.py` into **2,027 logical patches** in **767 distinct 1.13c functions** (some are data tables in `.data`).

Logical kinds: `callfix` 677 (the rel32 of an existing call now reaches D2Sigma), `ptr` 471 (an address in game code or a game
table now points at D2Sigma data), `nop` 380, `const` 284 (an immediate or a table bound), `byte` 144, `jmp` 58, `call` 13.

**Hook stubs.** Many targets lie in `0x1009b4b0..0x1009be50`: tiny naked-asm stubs (the symbol file wrongly names them
`D2Party_1009b4b0+0x..`). The real replacement is what the stub calls; `tools/sigma_patches.py` resolves each as
`STUB[calls X; resumes Y]`. The Ghidra export of D2Sigma (Sep 21 build) does not match the installed `D2Sigma.dll` (Oct 2 build) above about
`0x1007eb00`, notably near `0x1008b1xx` and `0x100bb6xx`-`0x100bb8xx`: stub names and `tools/sigma_fn.py sigma` output are unreliable there, so those entries were read from the installed DLL with `tools/disasm.py`. The 1.13c function table is also mislabelled for the AI patches (D2R's `monai.txt` order differs from 1.13c's).

## 2. Method

1. `tools/sigma_patches.py` dumps the 19 tables and groups the writes (above). For each patch it also records the 1.13c function
   (Ghidra export + `symbols.csv`), the original instruction (capstone, from the installed 1.13c DLL), the original callee, the
   D2Sigma target and the stub's callee / resume address. `tools/sigma_fn.py` prints the decompile of the function that contains
   an address (1.13c or D2Sigma).
2. The patches were grouped by 1.13c function (767 dossier entries, 17 chunks). For each function the original code and the
   replacement were read, the player-visible change was decided (Median vs vanilla 1.13c), and the port was searched
   (`plugin/src`, `docs/`, `tools/txt_migrate.py`) for the same behaviour. Rows group functions that belong to one feature.
3. Status vocabulary: **ported** (the plugin reproduces it; file and hook given), **data-equivalent** (the behaviour arrives through
   converted txt/bin columns), **D2R / D2RLoader does it** (D2R already behaves that way: raised limit, fixed bug, an own table,
   SDK feature), **missing** (Median behaviour a player would notice, not reproduced, and nothing in the plugin or docs covers
   it), **not applicable** (classic UI/800x600 layout, video and Glide/DDraw/D3D fixes, Battle.net/realm/launcher code, Warden,
   1.13c bugs D2R fixed, classic packet and save formats D2R replaced), **uncertain** (could not be decided from the code alone;
   section 6 says what settles each).
4. "Sites" counts the logical patches; "functions" counts 1.13c functions; "rows" are the audit rows (a row can cover several
   functions). The status of a row applies to all its sites.
5. Confidence is per row in the TSV (`high` / `medium` / `low`). Most `missing` rows were checked against the plugin source; a
   handful are low confidence and say what would settle them. No game was run for this audit (static reading only); section 6 says which rows an in-game check or a look at D2R's own code would settle.

### 1. Magic, rare, unique and set items drop identified

* **Median** (game1-003, game1-008, game1-013, game1-014): D2Game `0x104c1` (magic), `0x15443` (rare), `0x13daa` (set) and the unique picker push `1` instead of `0` into `SetItemFlag(item, 0x10 identified)`. Every non-normal drop is born identified: no Identify scroll, no Cain trip, names and mods readable on the ground.
* **Port now:** `item_gen.cpp` has the flag setter (`0x36d8f0`, item / mask / on) but nothing sets the identified bit; items drop unidentified as in D2R.
* **To do:** In the item-create hook that already sets ethereal / sockets, call the setter for qualities 4-8 (read D2R's identified bit from the dump; 1.13c uses `0x10`).
* **Overlap:** same gap as the unported.md row Auto-identify (audit IT3) of audit-rules; this audit pins the mechanism: the flag is pushed at generation
* **Impact:** high

### 2. Sockets and automagic for every quality

* **Median** (game1-009, game1-010): D2Sigma nops the `quality 1..3` guard (D2Game `0x10c95`, 9 bytes) and replaces the socket and automagic dispatch. The socket call is `0x1007e240(game, genRecord, item)` (stub `0x1009bc00`): the base's items record flag (D2R `+0x147`) must be set; then `qualities.MaxSock = 0` (rows 1-4: low / normal / superior / magic) rolls `rand() % 7` (0 = none, otherwise that many, cut to the item's maximum by setter `0x100800b0`; the generator's no-socket flag `+0x80 & 8` is read in this branch only), and `MaxSock = 1` (rows 5-9: set, rare, unique, crafted, tempered) rolls no die, does not read the generator flag and always asks for 6 (cut to the item's maximum); only a unique whose row has the flag `0x10` is skipped. **Correction of the earlier reading:** the `0x10` flag of Sigma's own `uniqueitems.txt` layout (enabled, nolimit, carry1, ladder, nosockets = bits 1, 2, 4, 8, 0x10) is `nosockets`, not `nolimit` (that is `0x2`), and `nosockets` is 0 in all 1834 rows, so every unique, set, rare and crafted item on a socketable base gets its maximum. `qualities.Automagics` (rows 1-9 all 1, stub `0x1009bbc0` -> `0x1007e0f0`) replaces the generator's quality switch for the automagic roll (item level 100+, base with an auto prefix group): D2R applies it to 1, 2, 3, 4, 6, 8, 9 and skips 5 and 7; Median applies it to all nine.
* **Port (lane pa-sockets, done):** `item_gen.cpp` hook `0x441fc0` rolls Median's rule for qualities 1-9; a two-byte patch at RVA `0x44356a` (the `jne` of the `quality 1..3` guard in `0x442d60`, `75 0e` -> `66 90`) lets qualities 4-9 reach it; the automagic jump table at RVA `0x44364c` (nine 32-bit RVAs, one per quality) is rewritten to the apply case for all nine qualities (Median's `Automagics`). Off word `allquals`; `mxl` line `item generation ... all qualities (...) patched`. D2R's own setter `0x375560` also caps by quality (measured: magic 4, rare 2, unique 1, crafted and tempered 3 sockets), which Median's setter does not, so the hook places the sockets itself (min of the roll and `0x36ead0`, flag `0x800`, stat `0xc2`). Game check `allqualsockets` (slot 3, 2026-10-22): 3000 items per quality at item level 101 on a 6-socket base: qualities 1-4 give 0..6 sockets evenly (1/7 each), 6-9 give 6 on every item, unique items carry an automagic mod (3000 of 3000); with `allquals` in `mxl-core-off.txt` the same check shows magic 0, rare / unique / crafted / tempered 0 sockets and unique automagic 0 of 3000. **Not seen:** a set item (the harness generator never returned quality 5 for any of the seven tried bases, it falls back to magic), so the set rows rest on the shared code path.
* **Deviation kept:** the hook leaves items of bases that cannot hold sockets (`0x373610`) or carry the no-socket base flag (`0x374660`) without sockets in every quality; Sigma's `0x1007e240` reads only the first of those.
* **Overlap:** overlap audit-rules (drops)
* **Impact:** high
