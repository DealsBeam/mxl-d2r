# Engine services map: what the port needs, who provides it, what could move to the SDK

Research for lane `services-map` (2026-10-22). Documentation only; no code changed. It answers three questions:

1. For every engine capability Median needs, **what provides it in the port today** (an SDK service, a D2RLoader / D2RCore built-in, our own hook or patch, data only, or nothing), and what breaks when D2R or D2RLoader updates.
2. Which **engine limits** the port touches, who raises each one, and where our workaround could collide with D2RLoader.
3. Which hooks could **move to SDK services**, ranked by effort and risk.

## Sources and how to read this

- Plugin: `plugin/src/*.cpp` of main at 93bbba8 (mxl-core 0.53.0): 45 `InstallInlineHook` call sites (5 of them are the diagnosis-only state trace; `monster_looks`, `quests_act2_5` and `calc_codes` install several through a loop or pair), about 20 `PatchWrite*` / `PatchBytes` sites, 2 `MutationService` transactions (`skill_tree.cpp`, `states_fix.cpp`), 5 import-slot or table-pointer swaps (`client_messages` packet table, `hirelings` NPC table writes, `item_events` D2RCore handler table, `mana_costs` call stub, `testharness` syscall stubs) and about 150 direct calls into D2R by RVA (`Fn<...>` or casts in `*_Rva` constants).
- Not on main yet: `strings.cpp` and the string-id thunk swap (branch `integ/ns`). Rows that depend on it are marked **[integ/ns]**.
- SDK: `third_party/PluginSDK` 0.3.0 (plugin ABI 4): 21 service ids (Lifecycle ... PluginCommunication), `core_exports.h` (ordinals 1-15), `reimplementation_exports.h` (2000-2007).
- D2RCore.dll 1.3.1 (timestamp `0x6ab37824`): export table read with a PE reader (764 named or ordinal exports). The private ordinals 1000-1373 are not an API (not in the SDK), but their names show what D2RLoader itself expanded. Strings of the DLL were searched for limit warnings.
- Docs: `plugin-spec.md`, `d2r-addresses.md`, `unported.md`, `subsystems/*.md`, `testing.md`, `bugs.md`. Off words are the ones `mxl_core.cpp` reads from `mxl-core-off.txt`. Checks are `tools/game_checks.py` names.

**Rule for every "yes" in the "Breaks on a D2R patch?" column.** All RVAs are for one image (PE timestamp `0x6ab3782c`, D2R 3.3 build 93847). `mxl_core.cpp` compares the image first; on a mismatch every engine hook stays off (the port degrades to data only, the `mxl` command says `MISMATCH, hooks off`). Hooks and patches also carry expected bytes, so a patch that moves one function turns that one feature off with a log line instead of crashing. Table-slot writes use an expected value of 0 and refuse to write over a filled slot. So "yes" means: the feature goes silent and the RVA table must be redone after the D2R patch. A D2RLoader update alone does not move D2R.exe RVAs; it only matters where a row says it touches D2RCore.

SDK column vocabulary: **none** = no SDK entry point does this; **partial** = an SDK service covers a part; a named service means a full replacement looks possible (feasibility is judged from the headers, nothing was built).

### The three highest-risk conflicts

1. **L8 item events**: writing into D2RCore's private handler table.
2. **L7 missile empty-slot stubs** and **L5 skill-table slots**: fail-safe on a changed slot, but a changed bound or a new D2R fill reopens the crash or silently disables a skill.
3. **L2 portals above level 255**: D2RLoader already ships 16-bit portal functions; our `+0x78` write is the older fix and may now double up.

## 4. Open questions found while writing

- **Set sizes (L10)**: count Median's sets from the built `setitems.txt`. If any set has more than six pieces, D2RLoader logs a warning and the extra members are the first thing to look at.
- **L2**: whether D2RLoader's `LinkTownPortal16` handles the portals made by our item spells and the Cow-level style portals. A one-line game check (create a portal to level 256+ with the harness) settles whether our `+0x78` write can go.
- **L8**: ask the D2RLoader author whether item-event registration will get an SDK entry.
- **Version drift**: D2RCore's timestamp is `0x6ab37824`, D2R.exe `0x6ab3782c`. Re-run the export scan (`pe_exports.py` in the session notes; any PE reader works) after each D2RLoader update and diff the 1000-1373 range for new `Wide*`, `16`, `Namespaced*` names.
